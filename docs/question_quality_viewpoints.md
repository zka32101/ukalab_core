## 選択肢の長さの手がかり（最も長い選択肢が正解になりがち）

対象は **選択式（`type: choice`）のみ**。仕訳・精算表・補助簿は対象外。

### なぜ問題か

正解だけを詳しく書く癖があると、内容を知らなくても「一番長い選択肢」を選べば当たる。誤答は短く言い切り、正解には条件や補足をつけがち、という書き手の癖が原因。学習では「長さで当てる」練習になり、模擬試験の点数も実力を表さなくなる（合否判定の妥当性を損なう）。

### 確認方法

選択式の問題について、次を集計する。選択肢数 n の問題で、無関係なら最長が正解になる確率は 1/n（4 択なら 25%）。

1. 最長の選択肢が正解の割合を、期待値（問題ごとの 1/n の平均）と比べる。
   - 同率最長は 2 通りで見る。**除外**（同率の問題を分母から外す）と**按分**（正解が同率に含まれたら 1/同率数 を数える）。
2. 最短の選択肢が正解の割合（逆の手がかり。誤答だけ長く作った場合に出る）。
3. 正解の長さ ÷ 他の選択肢の平均長 の中央値（1.0 付近が理想）。
4. 二項検定の目安: 同率でない問題について、最長が正解の回数が偶然（確率 1/n）より多いかの片側 p 値（n が問題ごとに違っても使える厳密計算）。
5. カテゴリ別（`subjectId` / `topicId`）の内訳。全体では目立たず、特定の章だけ偏ることがある。
6. 併せて正解位置（ア〜エ）の偏り。

長さは前後の空白を除いた文字数（Python の `len`）。目安なので厳密さは求めない。

### 判定の目安（暫定）

- 最長が正解の割合が期待値より **10 ポイント超**高い、または **p < 0.01** → 是正対象の候補。
- カテゴリ別で同じ基準を超える群がある場合も是正対象（ただし 20 問未満の群は参考値）。
- 最短が正解の割合が同様に高い場合も、逆の手がかりとして確認する。

**これらのしきい値は暫定**。実データで運用して様子を見てから見直す。数値を超えても自動で不合格にはせず、人が問題文を見て判断する（スクリプトも終了コードは常に 0）。

### 是正方針

- 誤答の選択肢にも、正解と同程度の具体性・長さを持たせる。
- 正解を簡潔にする（修飾や補足を削る）。
- 選択肢の長さをそろえる。
- **選択肢のシャッフルでは直らない**（長さは位置と無関係）。
- 誤答を不自然な長文にして「最長が誤答」という逆の手がかりを作らない。書換え後は再集計して確認する。
- 書換えで正解本文・正解位置・選択肢数が意図せず変わっていないことを前後比較する。

```bash

# フィールド名が違うアプリ
python3 tools/question_quality/choice_length_bias.py q.jsonl --choices-key options --answer-key answer --category-key topicId
# しきい値は暫定（既定 --margin 10 --alpha 0.01 --min-n 20）
```

実行例（手書きの 6 問。最長を正解にした問題を多めに混ぜたデータ。`--min-n 3` で小標本の注記を外している）:

```
## 全体（選択式 6 問）
- 最長が正解: 同率除外 4/6 =  66.7%（期待  25.0%、差 +41.7pt） / 按分  66.7%（期待  25.0%） / 同率 0 問 / 片側 p = 0.0376
- 最短が正解: 同率除外 0/1 =   0.0%（期待  25.0%、差 -25.0pt） / 按分  13.9%（期待  25.0%） / 同率 5 問 / 片側 p = 1.0000
- 正解長 / 他選択肢平均長 の中央値: 7.06（1.00 付近なら手がかりなし）
- 正解位置: ア:3(期待1.5) イ:0(期待1.5) ウ:2(期待1.5) エ:1(期待1.5)
- 判定: 要確認（是正対象の候補）
```

（以降 `subjectId=` ごとの内訳が続く。6 問では p 値は参考にならない。実データは数百問単位で見る。）
`example/sample_questions.jsonl`（4 問、全選択肢が同じ長さ）では「同率除外 0/0」で判定対象なしになる。

### 関連

- 次節の**断定語バランス**: 本観点（長さ）と同じ「選択肢の書き方の癖で当てられる」系統なので、レビューでは両方を続けて確認する。断定語を外すために誤答を言い足すと長さの偏りが逆転しうるため、是正後は両方を再集計する。
- `validate_content`: 形式の検査。本観点は意味の偏りを見るので重複しない。

## 選択肢の断定語バランス（断定語・否定の言い切りが誤答に偏る）

対象は選択式（`type: choice`）のみ。

### なぜ問題か

誤答だけに「必ず」「のみ」「すべて」などを付ける（または正解だけ「場合がある」と濁す）癖があると、内容を知らなくても断定語の有無で正誤が当てられる。長さの偏りと同じく、模擬試験の点数が実力を表さなくなる。

### 確認方法

断定語を含む選択肢の割合を、**正解の選択肢**と**誤答の選択肢**で比べる。

- 基本語: だけ / のみ / 全て / すべて / 必ず / 常に / 一切 / 全く / まったく / 絶対 / 決して
- 拡張語（既定で有効、`--no-extended` で外す）: 唯一 / 完全に / 全部 / 例外なく / いつも / 無条件 / 一律 / 常時 / 一度も / 二度と
- 否定の言い切り（`--negation` で有効）: ではない / できない / しない / ならない / ありえない / 存在しない / 含まれない / 起こらない / 不可能 / 認められない
- 断定にならない語句は照合前に除く（非常に・必ずしも・絶対値・絶対温度・絶対評価 等。`--exceptions` で追加）。
- 語リストは `--words-file`（1行1語）で差し替え、`--add-words` / `--exclude-words` で増減できる。アプリ固有の頻出語（例: 法令の「〜に限る」）は各アプリで足す。

判定: 含有率の差が **10 ポイント以上**、かつ両側 Fisher 正確確率検定で **p < 0.05** → 是正対象の候補。カテゴリ別（`subjectId` など）にも同じ基準で出す（20 問未満の群は参考値）。誤答に偏る場合も正解に偏る場合も警告する。選択肢は同じ問題の中で独立ではないため p 値は目安。**しきい値は暫定**で、数値を超えても自動で不合格にせず、人が問題文を見て判断する。

### 是正方針

- 誤答にも正解と同じ割合で断定語が入るよう、または双方から断定語を除くよう書き換える（誤答だけ・正解だけにしない）。
- 断定語を外すために誤答を言い足すと長さの偏りが逆転しうる。是正後は**長さと断定語の両方を再集計**する。
- 書換えで正解本文・正解位置・選択肢数が意図せず変わっていないことを前後比較する。

### 集計スクリプト

`tools/question_quality/assertive_word_bias.py`（Python 3 標準ライブラリのみ）。入力・フィールド名のオプションは `choice_length_bias.py` と同じ。


出力例（架空の偏りサンプル `tools/question_quality/testdata_biased.jsonl`）:

```
## 全体（選択式 40 問）
- 断定語を含む選択肢: 正解 0/40 =   0.0% / 誤答 120/120 = 100.0%（誤答 - 正解 = +100.0pt、両側 p = 0.0000）
- 語別（正解/誤答）: 必ず:0/40 だけ:0/40 すべて:0/40
- 判定: 要確認 誤答に偏り（断定語がない選択肢が正解になりやすい）（是正対象の候補）
```

## 重複・類似

- **完全一致**: `qid`、問題文、選択肢（問題内）の重複。0 件が前提。
- **同一論点**: 問題文は別でも、正解と論点が同じ問題（例: 交差エントロピー誤差を問う 2 問）。正解の文言が同じ組、選択肢の集合が同じ組を一覧にして、人が「定義型」「適用型」など角度が違うかを判断する。
- **近似文**: 2-gram などの類似度が高い組。「A法／B法に関する最も不適切なもの」のような**定型の兄弟問題**は、論点が別なら重複ではない（意図的な対を区別する）。
- 同じ選択肢セットの使い回しは、暗記で解けてしまうので、問いの角度が違うか確認する。
- **是正**: 角度を変える（定義→適用、用語→具体例）か、未収録論点の問題に差し替える。差し替えは分野・細目の配分と用語集の紐づけを崩さない範囲で最小限にする。

## 不足（分野・単元の偏り）とシラバス収録

- **分野・単元別の問題数**を集計し、試験の出題比率と照らす。1 単元が平均の数分の 1 しかない場合は不足の候補。
- **形式の偏り**（例: 簿記の仕訳が約 7 割、漢検は「漢字を選ぶ」1 形式のみ）と、**級・科目ごとの 0 問**（漢検の上位級の模擬試験など）も見る。
- **難易度の分布**（難問が少ない等）。
- **シラバス（出題範囲）の収録**: 資料が手元にあれば突き合わせる。無い場合は公式の出題範囲の知識による**推定**とし、**データ事実と推定を区別して記録する**。キーワード検索は表記ゆれ（ノーコード／ローコード、サーバレス／サーバーレス、条番号の表記）を考慮し、0 件でも「欠け」と断定しない。
- 出題範囲の改定がある試験（簿記 3 級の 2027 年改定など）は、旧区分表のみの項目を `levelId` 等で区別し、新区分表の出題プールに混ぜない。

## 選択肢の数・正解位置のバランス

- 選択肢数が問題間で不統一でないか（原則 4 つ）。
- 正解位置の分布が均等か（全体と、章・科目別。連続して同じ位置が続く最大長も見る）。表示側でシャッフルする設計でも、**元データが 1 つの位置に固定されていないか**を確認する（漢検の模擬試験は全問が A だった）。
- 並べ替えるときは `answerIndex` の追従と、「上記すべて」など順序に依存する選択肢が無いことを確認する。

## 答えの漏れ（問題文・ヒントに答えが出ている）

- 問題文や括弧書きのヒントに答えの字・語がそのまま含まれていないか（例: 「ケン」を表す漢字（健康の健）→ 答え「健」）。
- 是正は、答えを含まない例示（「＿康」の＿）に変える。自動チェック（正解の文字列が問題文に含まれる件数）を回帰テストにできる。

## 同音字・同義の誤答（正解が2つ成立）

- 書き取りなどで、誤答の選択肢に**正解と同じ読み（追加の読みを含む）を持つ字**が入ると、正解が複数成立する。誤答は正解の読みと共有しない字から選ぶ。
- 誤答に置き換えた語が、別の熟語として成立していないか（自動チェックは手元の用例データ内に限られるので、最終的には国語の専門確認が要る）。
- 選択肢どうしが同義、または包含関係にならないか。

## 用語集との紐づけ

- `relatedQuestionIds` が空の用語、問題の内容と無関係な紐づけ（例: ハルシネーションの問いが「AI 投資の動向」の用語に付いている）、存在しない問題 ID（リンク切れ）を確認する。
- 同じ概念の用語が 2 つに分かれている場合は、ID を壊さず統合せず、差異を記録する。
- 紐づけの修正は ID だけを変え、用語の定義文の事実は変えない。

## 事実性・専門確認と作り方の原則

- **事実を新たに作らない**: 是正（誤答の言い換え、並べ替え、重複の差別化）は、問題の論点と正解の正しさを変えない。誤答は「同程度の長さ・具体性の明らかな誤り」にする。外すと真に近づく（誤りの意味が変わる）修正は行わず、一覧にして残す。
- **問題を追加するとき**: 一般に確立した知識だけを使い、公式の過去問・シラバスは転載しない（自作）。法令・規格の条番号・年次・数値など誤りやすい事実は確実なものだけにし、根拠が弱い問題は作らない。計算問題（仕訳など）は貸借一致などを**スクリプトで検算**する。
- **専門確認**: 全問が自作の仮データであるアプリは、公開前に有資格者・専門家の確認が必須。専門確認が必要な問題（特に法令・規格・数値を含むもの）は優先度をつけて手順書（例: 情セマネの `docs/content_review_checklist.md`）に載せる。変更した問題は前後の文を PR 本文に載せ、確認の材料にする。
- AI 生成の素材（画像など）は、公開・ストア申告の前に、利用規約・商用利用の可否・AI コンテンツの申告を人が確認する。

## レビューの進め方

- **集計は必ず最新の `origin/main` で行う**。ローカルの作業コピーは古いことがあり、実際に乙4 の「正解が最長 98%」が古い数字（是正済み）だった。`git fetch origin +refs/heads/main:refs/remotes/origin/main` で参照を更新してから、専用の worktree を使う（通常の `git fetch origin main` だけでは `origin/main` が更新されないことがある）。
- **指標の数え方をそろえる**: 「単独最長」と「同率込み」では値が大きく変わる。比較するときは同じ数え方にする。期待値は選択肢数 n の 1/n（同率込みは高くなる）。
- データの事実と推定を区別し、専門判断・実機・本番データは「未確認」と明記する。
- 是正 PR は「CI が全緑」＋「変更した問題の前後を PR 本文に記載」＋「専門確認が必要な点を明記」。マージはユーザーの明示的な指示があるときだけ。
- 本番の Firestore などに反映するデータ（漢検のシードなど）は、PR のマージだけでは変わらない。再投入の手順と、実行は人が行うことを PR に書く。

## CI で警告として実行する

2 つのツールは、問題を追加するたびに CI で自動実行できる。**初期は警告のみ（失敗させない）**。しきい値が暫定のためで、運用して様子を見てから `strict` を検討する。

- 両ツールの終了コードは既定で 0。`--strict` を付けたときだけ、警告があれば 1。
- `--annotate`（GitHub Actions 上では自動）で、要確認の群を `::warning::` 注釈として PR に表示する。結果の全文は Actions の Summary にも出る。
- ローカルで 2 つ同時に回す入口: `python3 tools/question_quality/run_checks.py 'assets/questions/*.jsonl'`（glob 可、一致なしでも失敗しない）。
- ツール自体のテスト: `python3 -m unittest discover -s tools/question_quality -v`（ukalab_core の CI で実行）。

### 各アプリへの導入（コピー不要・1 ジョブ）

アプリの `.github/workflows/` に次を追加する（問題データのパスだけ書き換える）。

```yaml
name: Question quality
on:
  pull_request:
    paths: ['assets/questions/**']   # 問題データの場所
jobs:
  question-quality:
    uses: zka32101/ukalab_core/.github/workflows/question-quality.yml@main
    with:
      files: 'assets/questions/*.jsonl'
      # フィールド名が違うアプリ: choices_key: options / answer_key: answer / category_key: topicId
      # 語リストを足す: extra_args: '--add-words 限る --negation'
```

- `files` は空白区切りで複数指定でき、glob（`**` 可）を展開する。
- `core_ref` でツールの版を固定できる（既定 `main`。タグ・SHA 可）。ツールだけの追加なので、**core の Dart のバージョン（pubspec のタグ）とは無関係**で、アプリ側の依存更新は不要。
- ukalab_core が private で呼び出し側から読めない場合は、リポジトリ設定（Actions > General > Access）で同一オーナーのリポジトリからの利用を許可する。それでも取得に失敗するときは `secrets: { core_token: ${{ secrets.CORE_READ_TOKEN }} }` で read 権限の PAT を渡す。
- reusable workflow を使わない場合の 1 行版（ukalab_core を別途取得している CI 向け）: `python3 <core>/tools/question_quality/run_checks.py 'assets/questions/*.jsonl'`
